# Shared contracts — v1

The source of truth is `src/shared/contracts.ts`. Owned exclusively by coordinator. Backend owns `src/server/**`, `src/app/api/**`, `migrations/**`, `scripts/**` (except coordinator scripts), `tests/backend/**`. Frontend owns `src/components/**`, `src/app/page.tsx`, `src/app/layout.tsx`, `src/app/globals.css`, `src/client/**`, `tests/frontend/**`, PRODUCT.md, DESIGN.md and design artifacts. Coordinator owns package/config/CI, shared types, docs, E2E and deploy. Reviewer starts read-only.

## HTTP
- No authentication. Env `JEV_LIMIT_REACHED=true|1` disables the app: `/` renders only a "Limite Jev raggiunto" page and live endpoints answer 503 `LIMIT_REACHED`.
- GET `/api/config` returns `{liveAvailable:boolean,limitReached:boolean}` (no credential detail).
- POST `/api/runs` StartSchema → SSE `data: <RunEvent>\n\n`. `run_id` comes from every event. Requires database and Jev; 503 when the limit switch is on. Persist each event before send.
- POST `/api/runs` body requires `email` (trimmed, max 254, validated; a missing or empty email is a 400). It is stored in the run state as `contactEmail` only: never sent to Jev, never in events or the card, returned only in `RunSummary.email` for the buttons "Contatta azienda" / "Invia resoconto" (mailto links built in the browser; no mail server).
- GET `/api/runs?ids=<uuid,uuid,…>` → `{runs:RunSummary[]}` (adds `clarificationRound`, `jevCalls`, `email`) for the given ids only (max 50, most recent first). Production never enumerates; with `NODE_ENV=development` it also returns the 30 latest runs. The browser keeps its own run ids in `localStorage`.
- POST `/api/runs/:id/mail` body `{kind:"summary"|"contact", note?:string(max 500)}` → `{sent:true,to}`. The recipient is never in the request: it is the `contactEmail` stored with the run. Text comes from fixed templates (`customerSummaryLines` / `contactLines`). Limits: 5 messages per run, 10 per recipient per 24 h (429). 503 `MAIL_NOT_CONFIGURED` without `SMTP_URL`+`MAIL_FROM`; 409 `NO_EMAIL`; 502 `MAIL_FAILED`. Every attempt is logged in `bf_mail` (metadata only). The company is told once per run (completed, or waiting for manual review) when `MAIL_NOTIFY_TO` is set. `GET /api/config` also returns `mailAvailable`.
- GET `/api/runs/:id` → RunSnapshot (the unguessable run id is the only access control).
- POST `/api/runs/:id/resume` ResumeSchema → SSE; answers or human decision or retry. Stable LangGraph thread_id = run id.
- Error HTTP 400/401/404/409/429/503 with ApiError. SSE failure run_failed; private error details never returned.

## Output card and PDF
`FinalCard` (the `run_completed` payload) also carries optional `brief` (first 800 characters), `profileName`, `requiredFields` and `jevCalls`; cards stored earlier simply lack them. `src/client/report.ts` turns a card plus the run's events into a `Report` (verdict, headline, explanation and next step from fixed templates; required fields as answer / in brief / missing; steps with duration, visit number and route taken). The on-screen card (`RunCard`) and the PDF (`src/client/pdf.ts`, pdf-lib, standard fonts, generated in the browser) both render that same report. No text is generated by a model.

## Events
Events validated with EventSchema; monotonic sequence per run; unique id, node + visit_id on node events (repeated visits distinct). Payload conventions: node_started `{input}`, node_completed `{output,duration_ms}`, state_updated `{patch}`, route_selected `{source,target,label?}`, run_interrupted `{kind:'answers'|'manual_review',questions?:FieldId[]}`, run_completed `{card}`, run_failed `{code,message,retryable}`. Interrupt node may start again on resume; must not repeat Jev calls there. Operational state comes only from events, business compatibility separately. Replay is client-only, no POST and no Jev calls; duration retains recorded timing while playback pacing can be adjusted. Deduplicate by id and sort seq. UI can fetch persisted snapshot after disconnect; retries use graph checkpoints, idempotency keys and run lock.

## Persistence and isolation
Postgres checkpointer and application run/event/answer tables; profile snapshot and model pinned on run. No production in-memory fallback. MemorySaver allowed only tests/demo generation. Atomic per-run lock, request id uniqueness, owner auth on every live endpoint. Two rounds maximum, bounded calls, unknown responses become manual review/missing information. Profile configurable on start, copied into durable state. Preview/production separate DB and secrets; explicit migration script, never build-time migrations.
